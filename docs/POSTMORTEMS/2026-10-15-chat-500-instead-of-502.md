# Postmortem: LLM upstream failures returned HTTP 500 instead of 502

- **Date of incident:** 2026-10-15
- **Date of postmortem:** 2026-10-16
- **Severity:** S2 (degraded — every chat/agent turn during an upstream outage
  returned the wrong status and a generic message)
- **Duration:** unknown start (code shipped with the circuit breaker in commit
  `8931770`, 2026-10-14); detected and fixed 2026-10-15. Window ≈ 1 day.
- **Author(s):** operator + AI reviewer
- **Status:** resolved, actions 1–2 closed, 3 open

## Impact

Every `POST /chat` and `POST /agent` request that hit an open circuit or a
Gemini timeout returned `500 INTERNAL` with body
`{"error":{"code":"INTERNAL","message":"Internal server error"}}` instead of
`502 UPSTREAM_FAILURE` with a user-actionable message. Measured during the
agent-safety probe run: 14/14 requests returned 500/502 mix while the breaker
was open (`docs/EVIDENCE.md`, agent-safety section). No data was lost or
corrupted; the failure was presentational and diagnostic. Affected users:
anyone using chat while Gemini was unreachable — count unknown, bounded by the
LLM rate limiter (10/min per client).

## Root cause

The error taxonomy was incomplete. `src/lib/errors.js` already had
`UpstreamError` (502) — used by the recommend path — but the chat path
re-threw raw errors from `callLLMJson`. The breaker's `CIRCUIT_OPEN` error
carried a `code` but no `status`, so `errorHandler` classified it as an
unexpected error → 500. Contributing factor: the agent-safety probe initially
*expected* the failure to look like a limiter 429, so a 500 was misread as a
probe bug rather than a product bug for one iteration.

## What went wrong in detection/response

- No alert distinguished 500-on-chat from real server bugs; a human reading
  logs found it. With Sentry absent (gap G-3), this class of error is only
  found during deliberate testing.
- The breaker itself logged `err.code=CIRCUIT_OPEN` at level 50 — correctly —
  but the HTTP status layer never consulted that code.

## What went right

- The breaker did its job: no requests hung, no Gemini quota was burned while
  the upstream was down.
- A regression test now pins the behaviour (`processChat` rejects with
  `status: 502, code: 'UPSTREAM_FAILURE'`).
- The self-contained drill (`drill-502.mjs`) reproduces the whole scenario in
  ~60 s with no real API key.

## Blamelessness check

Writing a second LLM call inside the JSON-parse catch (the earlier design) was
rational: corrective prompting is the standard fix for malformed model output.
The mistake was not scoping that catch to parse errors only, and no test
enforced the boundary. The system change that makes this harder to repeat:
transport failures now propagate before the parse path runs, and a test pins
the 502 mapping — a future refactor that re-merges the paths fails CI.
